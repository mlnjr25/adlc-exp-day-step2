**Title:** Real-Time Currency Conversion & Audit Trail

**Business Idea:** Treasury operations teams at our enterprise customers
currently convert currency using manual lookups against a third-party
portal — slow, and it leaves no record for compliance. We need instant,
self-serve conversion inside our own app, and because these are regulated
transactions, every conversion must be reconstructable for an auditor on
demand, not pieced together afterward from emails or spreadsheets.

**Persona:** Treasury operations analysts at enterprise customers, who
process multiple cross-border settlements a day and are personally
accountable if a conversion can't be justified during an audit.

**User Need:** See a trustworthy converted amount the moment I enter it
— and be able to pull up any past conversion, with its rate and timestamp,
the moment an auditor asks for it.

**Known Constraints:**
- Frontend must read `VITE_API_URL` dynamically at container runtime using
  a generic entrypoint script placeholder replacement; replace the placeholder token
  `__VITE_API_URL__` inside the built `index.html` (or equivalent) with the runtime
  `VITE_API_URL` value.
- Backend must read database configurations exclusively from runtime
  environment variables.
- Backend must query external currency conversion data exclusively using a base URL from an environment variable (`CURRENCY_API_BASE_URL`), defaulting to an unauthenticated open-source endpoint like Frankfurter (`https://frankfurter.dev`).
- The application must not hardcode third-party API response schemas; utilize flexible JSON property mapping or an abstraction layer to isolate internal compliance tracking from external JSON structure changes (such as `rates` vs `conversion_rates`).
- The audit trail record must capture the exact execution timestamp generated by your backend server alongside any date or sequence markers returned by the external provider, ensuring complete sub-second audit reconstruction even if the provider only exposes a calendar date.
- External HTTP calls must handle failures gracefully with fallback values or clear domain exceptions rather than bubbling up raw network or serialization errors.
- CI/CD pipeline must inject placeholders safely at deployment time without
  exposing sensitive data in container layers.
- Restricted to specific stack versions: React (Vite/Node 24.*) and C#
  (**backend must target `net10.0` for build/test; CI must use `dotnet-version: 10.0.x`**).
- Must adhere to a strict folder layout (`src/frontend` and `src/backend`).
- A .NET solution file must always be generated at `src/backend/OuterloopLabApi.sln` via `dotnet new sln` + `dotnet sln add`, with the backend project added to it, and CI/build/test commands must invoke this `.sln` rather than the `.csproj` directly.
- Deploy as a single Azure Container App using the sidecar pattern to host
  both frontend and backend.
- Authenticate to Cosmos DB exclusively using token-based authentication via the pre-assigned User-Assigned Managed Identity, instantiated using `DefaultAzureCredential` configured with the specific `ManagedIdentityClientId`. Absolutely zero connection strings, master keys, or account keys are permitted in code, configurations, or logs.
- Utilize `Microsoft.Azure.Cosmos` and `Azure.Identity` packages for
  secure, token-based database interactions, including data-plane CRUD operations like adding and deleting items.
- Include `Azure.ResourceManager` and `Azure.ResourceManager.CosmosDB` packages to programmatically provision the Cosmos DB database and container via the control plane inside the application startup lifecycle (`Program.cs`) before the web application runs, utilizing the same token-based Managed Identity credentials for authentication.
  - ARM provisioning is best-effort; Managed Identity RBAC for ARM may differ from data-plane RBAC.
  - CRUD (and data-plane creation if needed) must be done via the Cosmos SDK (data-plane) using token-based Managed Identity credentials; access keys must not be used.
  - After ARM attempt, startup must run token-authenticated data-plane `CreateDatabaseIfNotExistsAsync` and `CreateContainerIfNotExistsAsync` and only proceed if the database/container are available (either already exist or were created). If token-authenticated data-plane create-if-not-exists fails, startup must fail.
- Map and bind all configuration values, including `AZURE_MANAGED_IDENTITY_CLIENT_ID`, endpoint URLs, and resource names, directly from the environment variables **using the exact keys** defined in `docs\CONTAINER_ENVIRONMENT_VARIABLES.md` without using local settings configuration files as fallbacks.

**Current Context:** The implementation should stay within `src/backend` and `src/frontend` and should use `src/backend/OuterloopLabApi.sln` for backend build/test orchestration, `src/backend/Program.cs` for startup wiring and Cosmos initialization, API/controller files under `src/backend/Controllers/`, domain/request/response models under `src/backend/Models/`, provider/repository services under `src/backend/Services/`, and automated tests under `src/backend/tests/` if a separate test project exists under the solution. On the frontend side, the feature should be implemented through `src/frontend/index.html`, a runtime placeholder-replacement entrypoint script under `src/frontend/`, and React application code under `src/frontend/src/` such as `src/frontend/src/main.tsx`, `src/frontend/src/App.tsx`, and a dedicated client module like `src/frontend/src/api.ts`. Assumption: if equivalent files already exist with different names, use those exact paths within the required folder layout rather than creating parallel duplicates.

**In Scope:**
- Add a backend endpoint that accepts amount, source currency, and target currency, calls the configured external FX provider, calculates the converted amount, and returns the normalized conversion response.
- Persist every successful conversion as an immutable Cosmos DB audit record containing the original request, normalized rate, converted amount, provider markers, and backend execution timestamp.
- Add backend read endpoints to retrieve a single audit record by identifier and to list recent conversion audit records in newest-first order.
- Introduce a provider abstraction layer so backend compliance logic is insulated from external JSON shape differences.
- Add frontend UI for submitting a conversion request, displaying the immediate conversion result, and viewing recent audit history plus a selected audit record.
- Implement runtime `VITE_API_URL` placeholder replacement for the built frontend so API routing is environment-driven at container startup.
- Add automated tests covering successful conversion, audit persistence contract, validation failures, and graceful provider-failure handling.

**Out of Scope:**
- Authentication, authorization, or tenant/user-specific access control.
- Updating or deleting previously stored audit records.
- Historical charting, reporting dashboards, CSV export, or batch settlement uploads.
- Multi-provider routing, rate caching, or background refresh jobs.
- Changes to deployment infrastructure outside the application code and required runtime placeholder flow.

**Feature Constraints:**
- Use `IHttpClientFactory` for outbound FX provider calls and isolate all provider-specific parsing inside a single adapter/service layer under `src/backend/Services/`.
- Use `decimal` for monetary and rate values; reject requests where `amount <= 0` or either currency code is not exactly three alphabetic characters after trimming and uppercasing.
- Return HTTP 400 with `ProblemDetails` for request validation failures, and HTTP 503 with `ProblemDetails` for provider/unavailable-normalization failures without exposing raw exception text, stack traces, or serializer details.
- Make audit history append-only in the API surface: implement create/read operations only and do not expose update/delete endpoints.
- Store enough data in each audit record to reconstruct the transaction without re-calling the provider: requested amount, source currency, target currency, normalized rate, converted amount, provider date/sequence markers, and backend execution timestamp.
- Order history queries by stored backend execution timestamp descending so the latest conversion appears first.

**Expected Outcome:** A treasury analyst can submit a conversion and immediately receive both the converted amount and a retrievable audit record. Example: a request `POST /api/conversions` with `{"amount":100.00,"fromCurrency":"USD","toCurrency":"EUR"}` and a normalized provider rate of `0.9200` with provider date marker `2026-08-01` returns HTTP 200 with a payload that includes `convertedAmount: 92.00`, `rate: 0.9200`, a non-empty `auditId`, the provider marker, and a backend-generated execution timestamp such as `2026-08-01T14:23:45.123Z`. A subsequent `GET /api/conversions/{auditId}` returns the same persisted values, and `GET /api/conversions?limit=10` includes that record in newest-first order. If the provider call fails, times out, or returns JSON that cannot be normalized into an internal rate model, the API returns HTTP 503 `ProblemDetails` with a clear domain-safe message and no raw transport/deserialization exception details.

**Expected Agent Output:** OpenCode should produce a buildable, testable change set under `src/backend` and `src/frontend` that includes solution-based backend updates via `src/backend/OuterloopLabApi.sln`, startup/configuration and Cosmos initialization changes in `src/backend/Program.cs`, backend controller/service/model/repository code for conversion submission and audit retrieval, frontend runtime placeholder replacement plus React UI for conversion and audit history, and automated tests verifying successful persistence and 503 failure handling.
